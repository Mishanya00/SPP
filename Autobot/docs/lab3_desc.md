# Лабораторная работа №3: дополнения к Автоботу

Изменения добавляют требования из `docs/lab3.txt` к существующему приложению. Генерация, автоматическое исправление Python-кода и запуск Telegram-ботов сохранены. Использованы имеющиеся Express, SQLite и `express-rate-limit`; единственная новая production-зависимость — **Nodemailer** для отправки писем через SMTP.

## 1. Три роли и временные ключи

В `users` добавлены `role` и необязательный уникальный `email`. По умолчанию существующие и новые пользователи получают `user`. Передать себе роль при регистрации нельзя.

| Роль | Доступ к ботам | Управление пользователями |
| --- | --- | --- |
| `viewer` | Просмотр только своих проектов, кода и логов; изменения запрещены | Нет |
| `user` | Создание и управление только своими ботами | Нет |
| `admin` | Просмотр и управление всеми ботами | Просмотр пользователей, назначение ролей |

Авторизация использует случайный 256-битный ключ сессии, действующий **7 дней**. Его SHA-256 хранится в SQLite, поэтому доступ можно немедленно отозвать. Браузер передаёт ключ в cookie `session` с `HttpOnly` и **SameSite=Strict**. Настройка `COOKIE_SECURE=true` включает передачу cookie только по HTTPS.

Для API ключ также возвращается как `accessToken` при входе/регистрации и принимается в `Authorization: Bearer <accessToken>`. Ответ содержит `expiresAt`. Ключ нельзя публиковать или сохранять в логах.

Роль проверяется на сервере при каждом запросе. `viewer` получает 403 при изменении проекта. Чужие боты для обычного пользователя выглядят как отсутствующие (404). При изменении **назначенной аккаунту** роли сессии пользователя отзываются; требуется новый вход. Понизить роль последнего администратора нельзя (409).

### Переключение активной роли и демонстрация прав

На основном экране в правом нижнем углу расположен блок с именем аккаунта и активной ролью: например, «Администратор (admin)». В нём доступны переключатель, ссылка на проверку прав и **«Активные сессии аккаунта»**. Также можно открыть `/access.html`: роль показана в разделе «Ваш аккаунт», а подключения — в разделе «Активные сессии».

Назначенная роль находится в `users.role`. Для демонстрации добавлена отдельная **активная роль текущей сессии** (`sessions.active_role`). Переключение не меняет назначенную роль, не завершает сессию и не затрагивает остальные подключения аккаунта. Новый вход начинает работу с назначенной ролью.

В обычном режиме доступны назначенная роль и более низкие роли: user может переключиться в viewer и обратно; администратор может выбрать любую роль. Для демонстрации **любым пользователем** задайте:

```dotenv
DEMO_ROLE_SWITCH=true
```

При включённом учебном режиме каждому авторизованному пользователю доступны viewer, user и admin. Эта настройка включена в локальной `.env` для текущей демонстрации. На странице явно отмечен учебный режим. Активная роль admin разрешает видеть и управлять всеми проектами и читать список пользователей, но назначать **постоянные** роли может только аккаунт с назначенной ролью admin. Выключение `DEMO_ROLE_SWITCH` ограничивает последующие запросы назначенными аккаунту правами, включая ранее повышенные учебные сессии. В `.env.example` учебный режим по умолчанию выключен.

На `/access.html` таблица показывает различия ролей и выделяет активную колонку. Кнопки «Проверить просмотр», «Проверить изменение ботов» и «Проверить доступ администратора» обращаются к серверу и показывают HTTP 200 или 403. Они используют те же правила доступа, что реальные операции, но не создают и не удаляют проекты.

Для демонстрации выберите viewer и проверьте изменение ботов (403), затем user (200), затем admin и проверьте доступ к пользователям (200). На основном экране изменение своего бота тоже запрещено для viewer и разрешено для user/admin.

HTML и JavaScript отдельной страницы раздаются без кэширования. При ответе старого API без `availableRoles` переключатель показывает текущую роль и объясняет необходимость обновления сервера, вместо пустого списка.

### Первый администратор

Сначала зарегистрируйте нужный аккаунт обычным способом. Затем задайте в `.env`:

```dotenv
ADMIN_USERNAME=имя_существующего_аккаунта
```

После перезапуска сервер назначит этому **существующему** аккаунту `admin`. Сама регистрация никогда не назначает администратора. `ADMIN_USERNAME` при последующих запусках повторно закрепляет эту роль; уберите настройку, если хотите управлять ею только через API.

## 2. HTTP-коды и обработка ошибок

Сохранён единый JSON-ответ с полем `error`. Дополнены проверки методов (`405` и `Allow`), заголовки авторизации (`WWW-Authenticate`), обработка некорректного `Origin` и больших файлов.

| Код | Когда возвращается |
| --- | --- |
| 200 | Успешное чтение, вход или изменение |
| 201 | Создан пользователь или проект бота |
| 202 | Принят запрос восстановления; также используется существующим повторным запуском генерации |
| 204 | Выход, отзыв сессии, смена пароля или удаление без тела ответа |
| 400 | Повреждённый JSON, некорректный Origin, недействительная/истёкшая ссылка восстановления |
| 401 | Нет действующей сессии или неверные учётные данные |
| 403 | Роль или источник запроса не разрешают действие |
| 404 | Не найден ресурс, сессия или разрешённый пользователю бот |
| 405 | Неподдерживаемый метод для существующего маршрута; допустимые методы указаны в `Allow` |
| 409 | Занятое имя/email, конфликт состояния бота или понижение последнего администратора |
| 413 | Слишком большое JSON-тело или загружаемый файл |
| 422 | JSON корректен, но поля не проходят проверку |
| 429 | Лимит запросов или временная блокировка входа; для блокировки указан `Retry-After` |
| 500 | Неожиданная внутренняя ошибка; подробности остаются в журнале |
| 502/503 | Недоступность внешнего сервиса или отсутствие необходимых настроек |

Порядок проверок: сначала аутентификация и права, затем обработчик ресурса. Поэтому закрытый маршрут может вернуть 401/403 до проверки допустимого метода. Генерация выполняется в фоне: HTTP-ответ о создании проекта не означает, что DeepSeek уже закончил работу; результат отражается в состоянии проекта и логах.

## 3. Защита входа, активные сессии и восстановление по email

### Защита от подбора

- Сохранён лимит **30 запросов за 15 минут с одного IP**. Теперь он применяется к регистрации, входу, восстановлению, смене пароля по ссылке и привязке email.
- После **5 неправильных входов за 15 минут** аккаунт блокируется на 15 минут. Последующие попытки получают 429, даже если пароль верный. Счётчики хранятся в SQLite и сохраняются после перезапуска.
- Успешный вход сбрасывает счётчик. После истечения окна счёт начинается заново.
- Для отсутствующего пользователя также выполняется вычисление scrypt с фиктивным хешем; сообщение об ошибке одинаковое.

IP берётся из `req.ip`; доверие произвольному `X-Forwarded-For` не включено. При размещении за reverse proxy настройку доверенных прокси нужно делать согласно своей схеме сети. Лимит IP хранится в памяти одного процесса; блокировка аккаунта — в базе.

### Контроль активных подключений

Под подключениями здесь понимаются активные авторизованные **сессии устройств/браузеров**, поскольку приложение работает через HTTP, а не постоянные пользовательские сокеты.

Одновременно разрешены **5 сессий на аккаунт**. При новом входе сверх лимита отзывается самая старая. Сохраняются время создания, последней активности, истечения, IP и User-Agent. Пользователь видит только свои сессии и может завершить любую из них. Идентификаторы в списке — хеши, а не действующие ключи доступа.

### Восстановление доступа

1. Пользователь заранее указывает email при регистрации через API либо на странице доступа, подтверждая текущий пароль.
2. Запрашивает восстановление по email. Для существующего и отсутствующего email штатный ответ одинаков: 202 с нейтральным сообщением; ссылка в HTTP-ответ не включается.
3. На зарегистрированный адрес отправляется письмо с одноразовым случайным ключом. В SQLite хранится только SHA-256 ключа и срок действия **15 минут**.
4. Пользователь открывает ссылку и задаёт новый пароль. Ключ проверяется и погашается в транзакции: два одновременных запроса не могут воспользоваться им дважды.
5. Все сессии и ссылки восстановления этого аккаунта отзываются, блокировка входа сбрасывается. Пользователь входит с новым паролем.

Пустая SMTP-конфигурация и ошибка отправки дают 503; неотправленный ключ удаляется из базы. Реальные письма при автоматических тестах не отправляются.

### Настройка SMTP

Поля добавлены в `.env.example`. Пример с условными значениями:

```dotenv
PUBLIC_BASE_URL=https://autobot.example.org
SMTP_HOST=smtp.example.org
SMTP_PORT=587
SMTP_SECURE=false
SMTP_USER=mailer@example.org
SMTP_PASSWORD=пароль_почтового_приложения
SMTP_FROM=mailer@example.org
```

На порту 587 используется обязательный STARTTLS. Для SMTP с TLS сразу при подключении обычно указывают порт 465 и `SMTP_SECURE=true`. Проверка сертификатов не отключается. `PUBLIC_BASE_URL` задаёт адрес ссылки в письме; он не берётся из пользовательского заголовка Host. Для локальной демонстрации допустим `http://localhost:3000`, если письмо открывается на той же машине. В реальном размещении используйте HTTPS и `COOKIE_SECURE=true`.

Для отправки используется [документация SMTP-транспорта Nodemailer](https://nodemailer.com/smtp/).

## 4. Структурированные журналы

Существующий JSON-логгер сохранён. Теперь журналируются также успешные GET-запросы API. HTTP-записи содержат время, уровень, сообщение, `requestId`, метод, маршрут, статус, длительность, а для авторизованных операций — `userId` и роль.

Добавлены события успешного и неудачного входа, изменения роли, привязки email, отзыва сессии, запроса восстановления и смены пароля. Маскирование расширено для `accessToken`, ключей восстановления и `SMTP_PASSWORD`. Тела запросов, пароли, cookie и содержимое писем не записываются.

## 5. Автоматическая проверка при изменениях

Команда:

```sh
npm ci --omit=dev --ignore-scripts
npm run check
```

`scripts/check.js` проверяет синтаксис JavaScript в `server/`, `public/`, `scripts/` и `tests/`, а также синтаксис Python в `runner/`. Затем выполняются все тесты через `node --test`.

Workflow GitHub Actions находится в **`../.github/workflows/autobot-check.yml`**, поскольку корень текущего Git-репозитория — `SPP`, а Автобот расположен в подкаталоге `Autobot`. Workflow в `Autobot/.github/` не запускался бы. Проверка автоматически запускается на push и pull request, затрагивающие проект или workflow; доступен ручной запуск. Используются Node.js 22.23.3 и Python, установленный в Ubuntu runner. Сборка React не включена: её исходники отсутствуют в восстановленном проекте.

## Как проверить лабораторную

1. Запустите `npm run check`.
2. После добавления настроек пересоберите приложение: `docker compose build app` и `docker compose up -d --no-deps app`.
3. Войдите администратором и откройте `/access.html`. Назначьте другому аккаунту `viewer`: после повторного входа чтение работает, а изменение ботов возвращает 403. Верните `user` и проверьте управление своим проектом.
4. Войдите несколько раз, посмотрите список сессий и завершите одну. Её ключ перестанет работать; чужую сессию отозвать нельзя.
5. Пять раз введите неверный пароль одного аккаунта. Следующий вход вернёт 429 и `Retry-After`.
6. Привяжите email, запросите письмо, измените пароль по ссылке. Старые сессии и повторное использование ссылки больше не работают.
7. После публикации изменений в GitHub проверьте выполнение workflow в разделе Actions.

## Проверки, выполненные при реализации

`npm run check` успешно проходит: проверка синтаксиса и **16 тестов**. Новые интеграционные тесты проверяют миграцию старой базы и сохранение сессии, роли и защиту чужих проектов, HTTP-коды, запрет назначения себе admin, защиту последнего администратора, лимит/отзыв сессий, блокировку аккаунта и IP-лимит, истечение ссылки восстановления и одновременное однократное использование ключа. Отдельно проверены JSON-формат логов, маскирование секретов и формирование SMTP-письма с TLS и настроенным адресом сайта.

Тесты используют временные базы и подменённую отправку писем. Исходная реализация лабораторной проверялась без изменения рабочей базы. При последующем добавлении переключателя образ приложения обновлён; в базе добавлена активная роль сессии, а существующие роли, аккаунты и Telegram-боты сохранены. Доставка через реальный SMTP и запуск workflow в GitHub требуют ваших почтовых настроек и публикации репозитория соответственно.
